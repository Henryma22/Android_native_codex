## 不可改变的优先级

本项目是个人 hobby/research 项目，首要目标是让 Codex 在 rooted Android 上真正可用，并尽快完成完整功能闭环：

1. 功能可用性；
2. 功能完整性；
3. 实现速度与后续可维护性；
4. 在不牺牲前三项的前提下加入合适的保护。

遇到问题时，必须先定位实际故障、恢复功能并评估具体风险。不能因为存在抽象的、低概率的或尚未证实的风险，就取消功能、缩减正常 Root 能力、引入永久拒绝门禁，或把整个 runtime 改成无法使用的安全演示版。

风险评估要区分“后果严重程度”和“发生概率”。本项目唯一需要持续优先防范的结果是手机启动能力被破坏、设备变砖以及由此造成的不可恢复损失。普通应用配置错误、依赖安装失败、服务退出或可恢复的数据问题，原则上通过提示、备份、回退和重试处理，不得升级成全局功能禁用。

## 固定实现路线

```text
CC Pocket 前端/交互
    → Android 本地生命周期与 session 管理
    → 用户配置的正常 KernelSU Root（可选非 Root）
    → PRoot Linux ARM64 用户空间
    → 官方 Linux ARM64 Codex CLI / app-server
    → OpenAI auth 或用户启用的第三方 provider
```

- 不把 PC、Bridge 或远程服务器放入 Android Codex 的正常运行链路。
- 不要求自定义 `codex_agent` SELinux 域，不强制固定组/capability，不把通用 broker 作为所有命令的必经路径。
- Root 是日常默认运行方式；非 Root 是用户可选模式。
- Codex 应能读取 Root 实际允许读取的 Android 宿主文件；普通文件和应用配置修改不设置泛化黑名单。
- PRoot 负责承载可独立升级的 Linux ARM64 用户空间和 CLI；Android 宿主命令、宿主路径与 guest `/` 必须明确区分。
- CLI、rootfs/依赖和 APK 分开更新；应用应依据实际 app-server/CLI 能力动态适配，而不是把版本锁死在 UI 中。
- OpenAI auth 与启用的第三方 provider 是互斥请求路径；第三方 provider 走 Codex 原生配置/协议，不在 UI 中伪造“已支持”能力。

## Root 与高风险操作

Root 权限不是功能缺陷的替代审批系统。正常命令不逐条弹 Root approval，设置页也不应因为打开页面就重复请求 Root。

对于 boot、启动分区、关键启动配置等可能影响启动能力的操作，采用软路由：

- 识别真实目标、设备/slot、影响范围和可用恢复手段；
- 对不可逆后果向用户说明，并取得这一次具体操作的授权；
- 能用可撤销 KernelSU 模块时优先使用，但不能因为模块路线不适用就永久阻断合法的必要功能；
- 必要时允许授权后的直接操作；
- 记录已完成的验证和剩余风险，不虚构“绝对安全”。

KernelSU profile、组、capability 和 SELinux 配置由用户负责。Agent 可以告诉用户需要检查什么，但不得为了自己的架构假设擅自修改 KernelSU 配置，也不得把某个自定义域当作项目成立的前提。

软路由是行为规范、目标验证和具体授权，不是新增一个覆盖所有 shell 命令的安全中间件。它不能被解释为对所有危险操作提供绝对防护，也不能被用作放弃功能实现的理由。

## 问题处理与验收纪律

后续每次实现遵循：

```text
实际错误/缺口
    → 定位根因
    → 先恢复可用功能
    → 评估具体风险与可逆性
    → 加入不妨碍功能的保护
    → 做定向验证
    → 记录证据和剩余缺口
```

- 优先解决阻断功能的问题；相邻但不影响当前目标的改进记入 backlog。
- 一次集中完成同一条链路，再构建和验证；不要每修一个小点就重复长时间全量编译。
- 真机连接时优先真机；模拟器只能证明模拟器路径，不能冒充真机 Root 验收。
- 构建成功、静态检查通过或 UI 显示“可用”都不能替代真实数据面验证。
- “一个阶段完成”不是自动停止条件。只要仍在用户已授权的总体目标范围内，并且没有新的外部阻塞，就继续推进下一个可完成的部分。
- 文档完成、goal 建立或某个局部测试通过，都不等于总体项目完成；必须明确列出已验证能力和未完成缺口。
